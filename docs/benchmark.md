# The benchmark

14 tasks over 7 public datasets. Each gives an agent a raw file, a data dictionary and a goal, and checks what it delivers against answers it never sees. This page is generated by `scripts/build_benchmark_doc.py` from the task specs in `src/pipeline_agents/bench/families/` and the checker validation run.

## How a task is checked

The agent must deliver `output/pipeline.py`. The checker copies the data and the agent's `.py` files to a fresh directory and re-runs the pipeline, so nothing made by hand counts. Then, stage by stage:

| stage | passes when |
|---|---|
| `clean_rerun` | `pipeline.py` runs from a clean copy |
| `predict` | `predict.py` runs on the hidden holdout, whose columns are only what is known at prediction time |
| `coverage` | every holdout row gets a prediction |
| `score` | the holdout metric beats the task threshold |
| `honest_estimate` | the agent's own validation estimate is close to the holdout metric |
| `answer` | an analytical answer matches the hidden answer, within tolerance |

Each threshold is set above the obvious baseline a practitioner would try first (for example the mean for each hour, or one strong column) and below every tree-based and one-hot linear model measured on that task, with one exception: on the bike forecast, linear models (MAE 66-80) do worse than the baseline and fail. Weaker models in between, such as boosting on the numeric columns only, can land on either side. The measured numbers are in the comments of each task spec.

## Traps

Which checker stage catches each trap. *score only* means falling for it lowers the score but is not guaranteed to fail the task.

**`bike-1-forecast`**

- `leak_casual_registered` (target_leak, caught by *predict*): casual + registered = cnt; neither is known before the hour happens, so the future features do not contain them (README: cnt includes both).
- `random_split_validation` (temporal, caught by *honest_estimate*): A random split puts neighbouring hours of the same days in train and validation, which understates the error of a forecast into later months.
- `int_coded_categories` (int_coded, caught by *score only*): season, weathersit, weekday and hr are codes, not quantities.

**`bike-2-weather`**

- `weathersit_codes` (int_coded, caught by *answer*): weathersit is a code 1-4 whose meaning is in the README.
- `normalized_temp` (semantics, caught by *answer*): temp is divided by 41; degrees Celsius need temp * 41 (README).
- `workingday_filter` (semantics, caught by *answer*): Only working-day hours count (workingday == 1).

**`adult-1-income`**

- `no_header` (format, caught by *coverage*): The file has no header row (README). Reading it with a header turns the first record into column names, and the same code then drops the first record it must predict.
- `leading_spaces_and_question_marks` (placeholder, caught by *score only*): Values follow ', ' separators, so categories carry a leading space; unknowns are '?'.
- `fnlwgt_is_a_weight` (semantics, caught by *score only*): fnlwgt is a sampling weight, not an attribute of the person (README).

**`adult-2-education`**

- `leading_space_unknowns` (placeholder, caught by *answer*): Unknowns are ' ?' after the separator, so comparing with '?' finds none unless the spaces are stripped.
- `unknown_occupation_filter` (semantics, caught by *answer*): Shares are over records with a known occupation only.

**`air-1-co-daily`**

- `minus_200_missing` (sentinel, caught by *answer*): Missing readings are -200 (README); averaging them in drags daily means far down.
- `decimal_comma` (format, caught by *answer*): Semicolon-separated with decimal commas: '2,6' is 2.6 (README).
- `day_first_dates` (format, caught by *answer*): Dates are DD/MM/YYYY; month-first parsing moves readings to the wrong day.

**`air-2-co-estimate`**

- `analyzer_columns_unavailable` (target_leak, caught by *predict*): Every (GT) column comes from the analyzer being removed (README), so none of them exists in the future features.
- `minus_200_target` (sentinel, caught by *score*): -200 marks a missing reading, including in CO(GT); training on those rows teaches the model to predict -200.
- `decimal_comma` (format, caught by *clean_rerun*): Decimal commas: parsed without decimal=',', the sensor columns are text.
- `random_split_validation` (temporal, caught by *score only*): Sensors drift over months; a random split overstates accuracy on later months. Not caught: honest estimates on this data also miss by 36-57%, so the honesty check is off.

**`bank-1-subscribe`**

- `duration_known_after_call` (target_leak, caught by *predict*): duration is only known after the call (README), so the clients to score before calling have no duration column.
- `pdays_999` (sentinel, caught by *score only*): pdays = 999 means never contacted (96% of rows), not a very long time ago.
- `unknown_categories` (placeholder, caught by *score only*): 'unknown' appears in job, marital, education, default, housing and loan.

**`bank-2-previous-campaign`**

- `pdays_999` (sentinel, caught by *answer*): pdays = 999 means no previous contact (README); averaging it in gives a mean near 960 instead of about 6.

**`diabetes-1-readmit`**

- `patients_repeat` (group_leak, caught by *score only*): patient_nbr repeats, so a row-level split mixes patients. Measured: it moves CV AUC by only 0.003 here, so the honesty check cannot catch it.
- `three_class_target` (semantics, caught by *score*): readmitted has three values; only '<30' is the positive class.
- `question_marks` (placeholder, caught by *score only*): Missing values are '?' (README).
- `expired_patients` (semantics, caught by *score only*): Patients who died (discharge_disposition_id 11, 19, 20, 21) are never readmitted.

**`diabetes-2-age-rates`**

- `one_row_per_patient` (group_leak, caught by *answer*): Rows are encounters, not patients; each patient must be counted once.
- `three_class_target` (semantics, caught by *answer*): Only '<30' counts; '>30' is a later readmission.

**`credit-1-default`**

- `two_header_rows` (format, caught by *clean_rerun*): The first line holds codes X1 ... Y and the second the names (README); reading only the first as a header turns every column into text.
- `undocumented_codes` (semantics, caught by *score only*): EDUCATION uses 0, 5 and 6, MARRIAGE uses 0, and PAY_* uses -2 and 0; none is in the README.
- `codes_not_quantities` (int_coded, caught by *score only*): SEX, EDUCATION and MARRIAGE are codes, not quantities.

**`credit-2-education`**

- `two_header_rows` (format, caught by *clean_rerun*): Two header rows; the names are on the second.
- `undocumented_codes_are_not_others` (semantics, caught by *answer*): Codes 0, 5 and 6 are not documented; folding them into 'others' (4) moves its default rate from 0.041 to 0.063 in this data.

**`retail-1-monthly-revenue`**

- `month_first_dates` (format, caught by *answer*): InvoiceDate is M/D/YYYY (README); day-first parsing moves the first 12 days of every month into other months.
- `cancellations_are_negative` (semantics, caught by *answer*): Cancellation lines (InvoiceNo starting with C) have negative quantities; dropping negative lines as 'bad data' overstates revenue.
- `invoices_not_lines` (semantics, caught by *answer*): A cancelled invoice has several lines; the count is of distinct invoices.

**`retail-2-repeat-buyers`**

- `features_from_the_label_window` (temporal, caught by *honest_estimate*): Training labels come from June-August, so training features must use transactions before 1 June only; features built from all transactions contain the answer.
- `cancellations_and_unknown_customers` (semantics, caught by *score only*): Cancelled invoices are not orders, and lines without a CustomerID belong to nobody.

## Known limits

- **`air-2-co-estimate` does not check honesty.** Honest time-based estimates missed the holdout by 36-57% (the validation months are more polluted than the holdout months) while a random split missed by 28%, so no tolerance separates them. The random-split solution is kept as `uncaught_random_split`.
- **`diabetes-1-readmit` cannot catch the patient group leak.** Row- and patient-level cross-validation differ by 0.003 AUC, because patients average 1.42 encounters.
- **`bank-1-subscribe` uses a random holdout.** The rows are time-ordered and the subscription rate climbs from 3% to 46% across the file, so a time-based holdout would mostly measure that shift.
- **The Bank Marketing data contradicts its own README:** 3,311 clients have earlier contacts but `pdays = 999` ("not previously contacted"), so `bank-2-previous-campaign` only asks unambiguous questions.
- Thresholds were set from one holdout draw each; margins to the nearest honest and broken solutions are in the spec comments.
