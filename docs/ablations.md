# Ablations: structure and memory, on the test split

8 test tasks x 3 seeds x 6 arms = 144 runs, on the split that was never used for tuning. Loop parameters and prompts were screened on dev only. Success means the pipeline runs from a clean start, passes every trap check and beats the task's threshold on the hidden holdout. Intervals are 95% from a nested bootstrap (tasks, then seeds); comparisons are paired on the same task and seed. Generated by `scripts/build_ablations_doc.py`.

| arm | what it is | success rate | revisions | model calls | shadow $ | seconds |
|---|---|---|---|---|---|---|
| baseline | one model writes the whole pipeline | 0.88 [0.67, 1.00] | 0.8 [0.1, 1.8] | 1.8 [1.1, 2.8] | 0.0016 [0.0007, 0.0028] | 152.9 [50.9, 346.0] |
| multi | the agent team, no memory | 0.50 [0.21, 0.79] | 3.3 [1.2, 5.8] | 23.0 [13.2, 34.0] | 0.0097 [0.0052, 0.0148] | 372.5 [200.9, 569.9] |
| memall | the team, all three memories | 0.71 [0.46, 0.92] | 2.5 [1.0, 4.3] | 20.9 [13.2, 29.6] | 0.0093 [0.0054, 0.0137] | 363.0 [213.2, 534.6] |

## Does the structure pay for itself?

| comparison | success difference [95% CI] | pairs | real? |
|---|---|---|---|
| baseline - multi | +0.38 [0.04, 0.71] | 24 | yes |
| baseline - memall | +0.17 [-0.17, 0.50] | 24 | no |

The single-agent baseline wins, and it costs about an order of magnitude less per run. The team's advantage was supposed to be repair; instead its extra calls buy revisions that often restate a problem the Executor cannot fix from inside one step.

All three stores together is the best of the team arms, but on these tasks only the gap to procedural-only is outside the noise. No single store is measurably better than no memory at all.

## How the runs stopped

| arm | failed | needs_human | succeeded | hit the memory limit |
|---|---|---|---|---|
| baseline | 1 | 0 | 23 | 0 |
| multi | 2 | 5 | 17 | 2 |
| memall | 1 | 3 | 20 | 1 |
| memproc | 2 | 4 | 18 | 2 |
| memsem | 2 | 3 | 19 | 2 |
| memepi | 0 | 4 | 20 | 0 |

**The memory limit matters for reading this table.** 7 runs were killed for exceeding the sandbox's 4 GB, all of them on the two widest datasets: six built a dense one-hot matrix from high-cardinality columns (the diabetes diagnosis codes, the credit categories), the seventh joined two large frames. The system counts a memory kill as infrastructure, retries the step and then abandons the run, so the agents never get told to use less memory. Those runs count as failures here, and they fall unevenly across arms memall: 1, memproc: 2, memsem: 2, multi: 2. Sending a memory kill to the Reviser instead is a change to test on dev, not something to introduce after seeing these results.

Two more runs were hurt by a validation tool that was too strict during these runs: `split_overlap` reported any identical rows in both halves of a split, though a couple of matching records is normal and only a large share means the same rows were split into both. One `retail-2` run spent its revisions and its re-plan on it and stopped for a human. The tool now reports a share and passes below 1%; that fix came after these runs and is not in these numbers.

## What this does not say

- 8 tasks and 3 seeds give wide intervals. Differences below about 0.2 in success rate are not measurable here.
- Memory arms start with the procedural skills mined from dev runs; facts and episodes start empty and are written by the run sequence itself.
- The Critic agrees only weakly with careful labels (see `docs/trust.md`), so a revision is not proof that a step was wrong.
- Shadow $ are token counts times a pinned price table, never money spent.
