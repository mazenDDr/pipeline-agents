The classes fall into three kinds, and the split matters more than the counts:

- **The agents' own mistakes**: a weak model, a crash they could not fix, a unit they ignored.
- **The system's design**: a loop that spends its budget on the last step when the fault is in an earlier one, and a memory kill treated as an infrastructure problem.
- **My harness and benchmark**: a profile note that invited deleting real rows, two validation rules that were too strict (both fixed), and a task whose text disagrees with its own answer.

## The model is not good enough

**29 runs.** Tasks: bike-1-forecast (13), adult-1-income (6), air-2-co-estimate (5), bank-1-subscribe (3), credit-1-default (1), diabetes-1-readmit (1).
Arms: multi (14), baseline (6), multi-r2 (5), memproc (2), memepi (1), memsem (1).

The pipeline ran and produced predictions for every holdout row, with its own estimate inside the honesty tolerance, but the model is weaker than the task's threshold. This is the largest class, and the only one where the agents did nothing wrong in the engineering sense.

Example, `memproc_credit-1-default_s3` in `t11-test-stores`:

```
holdout roc_auc 0.7384, threshold 0.755; its own estimate (0.7775) was better than the holdout (0.7384)
```

**What would fix it.** Nothing in the loop will fix this: it needs better modelling (features, hyper-parameters, a stronger learner). The system never compares its model against a simple baseline model, so it cannot tell a weak model from a good one.

## The loop ran out on predict.py

**15 runs.** Tasks: retail-2-repeat-buyers (6), adult-1-income (3), diabetes-1-readmit (3), credit-1-default (2), air-2-co-estimate (1).
Arms: multi (8), memsem (3), memepi (2), memproc (2).

The pipeline was built, then the delivery check found that predict.py cannot read the real input format, and the run spent both revisions and its one re-plan on the last step. The fault usually lives in an earlier step (the training features were built from a file that predict.py never sees), and the Executor of the last step cannot reach it.

Example, `multi_adult-1-income_s1` in `t9-dev`:

```
s7 still rejected after 2 revisions: ["delivery check predict_smoke failed: predict.py failed on 200 rows of smoke_features.data (nonzero_exit): stdout: Error during prediction: columns are missing: {'age', 'occupation', 'capital-gain', 'workclass', 'relationship', 'race', 'capital-loss', 'hours-per
```

**What would fix it.** Let the Reviser reopen the step that owns the artifact predict.py needs, or add a repair mode that may rewrite the whole pipeline instead of one step. Tell the Executor the input format at the step that writes predict.py, not only when the delivery check fails (this was added in T11 and cut the class, it did not close it).

## Cleaning deleted real data

**14 runs.** Tasks: retail-1-monthly-revenue (14).
Arms: multi (3), memepi (3), memproc (3), memsem (3), memall (2).

A cleaning habit that is usually right destroyed real records. The dataset profile reported '2,483 exact duplicate rows'; 14 of the 15 team runs removed them and all 14 failed, the one team run that kept them passed; in this file identical lines are real repeated scans of one item on one invoice, so December 2010 lost 2,233.41 of revenue. The baseline, which sees the same profile but writes one program, kept them in all three runs.

Example, `memall_retail-1-monthly-revenue_s1` in `t11-test-core`:

```
net_revenue_by_month.2010-12: got 746723.61, want 748957.02
```

What the code did: the clean step ran drop_duplicates() on the transaction lines. In this file identical lines are real repeated scans of the same item on one invoice, so 2,483 real lines were deleted and December 2010 lost 2,233.41 of revenue (746,723.61 against 748,957.02, which is exactly the de-duplicated total). The dataset profile had reported '2,483 exact duplicate rows'. No baseline run dropped them, and all three passed.

**What would fix it.** Fixed here: the profiler now says that repeated records can be real and that the meaning of a row should be checked before dropping them. This came after the runs, so it is not in their numbers. A cheaper guard: the answer step could report how many rows it dropped since the raw file, which the row-count tool already does for clean steps but not for analysis steps.

## Killed by the memory limit

**7 runs.** Tasks: diabetes-1-readmit (6), credit-1-default (1).
Arms: multi (2), memproc (2), memsem (2), memall (1).

The step was killed for using more than the sandbox's 4 GB, always by building a dense one-hot matrix from high-cardinality columns or joining two large frames. The system counts a memory kill as an infrastructure problem: it retries the same step, then abandons the run, so the agents are never told to use less memory.

Example, `memall_diabetes-1-readmit_s1` in `t11-test-core`:

```
infra: s4 failed 4 times
```

**What would fix it.** A memory kill caused by the step's own code is a logic failure: send it to the Reviser with the limit and the step that hit it. Keep infrastructure retries for what the agents cannot control (a dead endpoint, a killed process).

## The benchmark is wrong

**6 runs.** Tasks: bank-2-previous-campaign (6).
Arms: baseline (2), multi (1), memepi (1), memproc (1), memsem (1).

The task text and the hidden answer disagree. bank-2 asks for the subscription rate of 'those clients' (the ones with a recorded pdays), which is 0.5 for the failure group; the hidden answer takes the rate over all clients with that outcome, 0.1365. Runs that followed the text were marked wrong.

Example, `baseline_bank-2-previous-campaign_s1` in `t11-test-core`:

```
subscription_rate_by_previous_outcome.failure: got 0.5, want 0.1364568081991215
```

What the code did: the task text asks for the rate among 'those clients' (the ones with a recorded pdays), which gives 0.5 for failure; the hidden answer takes the rate over all clients with that poutcome, which gives 0.1365. The runs that followed the text were marked wrong. The benchmark is at fault, not the run.

**What would fix it.** Fixed here: the task now says 'all clients with that outcome'. The reference answer is unchanged, and the benchmark solutions still behave as expected. The T11 numbers were measured with the old wording.

Arms: memall (3), memepi (2), memproc (1).

A step kept crashing and neither two revisions nor a new plan fixed it. The Reviser sees the traceback, but its instructions go back to the same Executor prompt for the same step.

Example, `memall_diabetes-1-readmit_s3` in `t11-test-core`:

```

```

**What would fix it.** Show the Reviser the artifacts the step read (columns and dtypes of its inputs), not only the traceback, so its instructions can name the mismatch.

## The baseline ran out of repairs

**4 runs.** Tasks: adult-1-income (3), diabetes-1-readmit (1).
Arms: baseline (4).

The single-agent baseline used all its repair attempts (the same budget as the team: 1 + revisions, times 1 + re-plans). This is the baseline's only structural failure class.

Example, `baseline_adult-1-income_s1` in `t9-dev`:

```
no passing attempt in 6
```

**What would fix it.** Nothing to fix in the team; it is the baseline's ceiling and belongs in the comparison.

## A documented unit was ignored

**4 runs.** Tasks: bike-2-weather (4).
Arms: multi (3), multi-r2 (1).

A documented unit or code was used raw: the normalized temperature (0.52) instead of degrees Celsius (21.30), although the data dictionary states the scaling. The Critic accepted the step with confidence 1.0; no validation tool reads the data dictionary.

Example, `multi_bike-2-weather_s3` in `t9-dev`:

```
mean_temp_celsius: got 0.5195654565456546, want 21.302183718371836
```

What the code did: the answer used the normalized temp column (0.52) instead of degrees Celsius (temp x 41 = 21.30), although the data dictionary states the scaling. The Critic accepted the step with confidence 1.0.

**What would fix it.** A tool that checks final answers against the dictionary's stated ranges and scalings would catch it. The Critic already has the dictionary in its prompt, and the T10 audit shows it does not use it for numbers.


**What would fix it.** The Planner is not told what the previous plan was rejected for in a form it can act on: pass the failed step, its evidence and the escalation reason as a short structured note, not one sentence.

## A reply could not be parsed

**2 runs.** Tasks: air-2-co-estimate (2).
Arms: multi-r2 (1), multi (1).

A role's JSON could not be parsed twice in a row: an invalid escape in the Reviser's reply. Both runs are the same seed of the same task.

Example, `multi-r2_air-2-co-estimate_s1` in `t11-dev`:

```
reviser output unusable after a re-ask on s7: invalid JSON: Invalid \escape: line 1 column 524 (char 523)
```

**What would fix it.** Fixed in T11: the Reviser's call now constrains the reply to its schema, as the memory writers do.

## The estimate the run trusted was far off

**2 runs.** Tasks: retail-2-repeat-buyers (2).
Arms: memall (1), memproc (1).

The holdout score passed, but the run's own validation estimate was far from it in either direction: 0.86 against 0.74, and 0.54 against 0.71. Both are retail-2, where features must come from before the label window.

Example, `memproc_retail-2-repeat-buyers_s1` in `t11-test-stores`:

```
validation 0.8621 vs holdout 0.7369 (gap 0.1252, tolerance 0.05); its own estimate (0.8621) was better than the holdout (0.7369)
```

**What would fix it.** The honesty rule is two-sided, so a pessimistic estimate fails like an optimistic one. Worth splitting the two in the checker report, because only the optimistic direction means the run fooled itself.

## What this list changes

1. A memory kill from the step's own code should reach the Reviser, not the infrastructure retry.
2. The Reviser should be able to reopen the step that owns a file the delivery check complains about, or rewrite the pipeline as a whole.
3. The profiler should present a duplicate count as something to check, not a defect to remove.
4. The bank-2 task text must be corrected to match its own answer.
5. Nothing in the loop addresses the largest class: the model is not good enough. A comparison against a simple baseline model, inside the run, would at least let the team know.
