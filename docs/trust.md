# Can the Critic and the checker be trusted?

Before tuning anything on the dev grid (`t9-dev`), two questions: does the Critic judge steps the way a careful reader would, and are the checker's failures real failures? Generated by `scripts/build_trust_doc.py` from the call logs and `outputs/trust/t10/`.

## The Critic

The dev grid made **181 Critic calls** (158 accept, 23 revise, 0 escalate). A stratified sample of 50 was labelled blind, without the Critic's decision, by answering one question: *can later steps build on this step as it is?*

| | value |
|---|---|
| agreement with the labels | 66% (50 cases) |
| Cohen's kappa [95% CI] | 0.30 [0.04, 0.54] |
| too strict (step was fine, Critic asked for a revision) | 13 |
| too lenient (step was wrong, Critic accepted) | 4 |
| estimated too strict, all 181 calls | 13 |
| estimated too lenient, all 181 calls | 43 |
| Critic confidence | 1: 179, 0.9: 1, 0.8: 1 |

Kappa near 0.3 is weak agreement. The estimates scale each stratum's error rate to its size among all calls; the lenient estimate rests on 4 of 12 labelled accepts and is rough.

| stratum | calls | labelled | agree | too strict | too lenient |
|---|---|---|---|---|---|
| accepted, a tool failed | 30 | 15 | 15 | 0 | 0 |
| accepted, no tool failed | 128 | 12 | 8 | 0 | 4 |
| revised, a tool failed | 10 | 10 | 1 | 9 | 0 |
| revised, no tool failed | 13 | 13 | 9 | 4 | 0 |

What the numbers say:

- **The confidence score carries no information.** It is 1.0 on almost every call, so the rule "confidence below 0.5 goes to a human" never fires.
- **Too strict, mostly because of one tool.** 9 of the 10 revisions that followed a failed tool were not needed. The row-count check compared every step with the raw file, so after one step dropped the rows with a missing target (on purpose, and accepted), every later step was flagged again for the same 21% drop. A loader that kept the file's 114 empty lines was flagged as a duplicating join. Unneeded revisions use up the revision budget and then the single re-plan: the two `air-2` runs that stopped at step s3 in T9 ended that way.
- **Too lenient where no tool looks.** The accepted mistakes are a `predict.py` that cannot read the real input (a headerless file read with a header, one-hot columns filled with zeros) and a wrong number (temperature left normalized). No validation tool runs on those steps, and the Critic does not execute the script.

One design note, not a bug: `honest_estimate` is two-sided, so a validation estimate that is too pessimistic (bike-1: validation 78 against holdout 61) fails like an optimistic one. In this grid it never decided an outcome, because the score failed first.

## What changed

- The row-count check now compares a step with the largest table of the closest earlier accepted step (the raw file only for the first steps), and a table that grew by exactly the raw file's empty lines passes with a note. Tests cover both, and the step test fails on the old comparison.

## Limits

- One labeller, labelled blind. With no second labeller, labeller error is not measured; the *why* column above makes every label checkable.
- The sample is stratified (23 of 23 revisions, 27 of 158 accepts), so the raw agreement over-weights revisions; the population estimates correct for that.
- Only failures were audited. A pass that should have failed is possible where a trap is marked *score only* (see `docs/benchmark.md`).
- The row-count fix is checked by tests, not yet by a re-run of the grid; that happens in T11.
